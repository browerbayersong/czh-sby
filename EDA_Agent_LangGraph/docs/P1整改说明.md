## 逐条说明

### 1. 汇总字段的解析与展示

`_parse_sim_log()` 从仿真日志提取：

| 字段 | 来源 |
| --- | --- |
| `checks_total / passed / failed` | `total checks = N, passed = M, failed = K` |
| `scenarios` | `scenarios:` 多行列表 |
| `random_seeds` | 所有 `seed=` 出现值（去重排序） |
| `functional_bins_hit/total` | `functional coverage = n/m bins` |
| `ended` | `TEST PASSED` / `TEST FAILED` |
| `finish_ps` | `$finish at simulation time` |

旧格式（v1 的 `OK at time`）仍兼容：没有汇总行时按逐行计数降级。

### 2. 快照与哈希

以 `vcs_017` 为例：

```
evidence/counter_v82/vcs_017/
├── snapshot_manifest.json   （2 条 SHA-256）
├── src/generated/rtl/counter_8bit.v
├── src/generated/tb/tb_counter_8bit.v
├── vcs_compile.log
├── vcs_sim.log
├── run_summary.json
└── coverage_dashboard.txt
```

复核方式：

```powershell
python -c "import hashlib,json,pathlib; d=pathlib.Path('evidence/counter_v82/vcs_017'); m=json.loads((d/'snapshot_manifest.json').read_text(encoding='utf-8')); print(all(hashlib.sha256((d/'src'/r).read_bytes()).hexdigest()==h for r,h in m['files_sha256'].items()))"
```

6 轮（`vcs_004/006/007/015/016/017`）均已验证一致。

**注意**：`runs/<label>/src/` 在 Linux 上还混有 VCS 编译生成的 `csrc/`、`cm.log`、`ucli.key`（约 27 项/轮），这些不在清单内，归档时已过滤，避免「快照 29 个文件、清单只有 2 条」的误导。

### 3. 早期轮次

`vcs_004` 是接入覆盖率后的基线（88.53%），`vcs_006` 是第 1 次优化（92.53%），`vcs_005` 是 v2 TB 自身缺陷导致的失败样本（57 处 `[FAIL]`），作为「失败轮次」保留。

### 4. 解析测试

`test_analysis_offline.py` 覆盖四类输入：

| 用例 | 断言 |
| --- | --- |
| v5 完整日志 | 1032/1032/0、11/11 bins、3 个种子、14 类场景、`TEST PASSED` |
| v1 旧格式 | 按 `OK at time` 计数，bins 为 `None` |
| 失败轮 | `failed=2`、`TEST FAILED`、`exp/got` 模式 |
| 汇总与导出 | `latest_passed/latest_bins` 正确，Markdown 含关键字段 |

运行：

```powershell
python test_analysis_offline.py
```
